## Context

帳冊只記稿件裡已有的文字。結構附檔的節與段都要用 first_prop 指到帳冊裡沒有退役的命題（S5），所以還沒寫的節與段放不進去，也沒有欄位放「這一段要說什麼」。construct 的 next 模式照 article-construction 規格不寫任何檔。

#75 要先定綱要、作者確認、再擴寫。維護者 2026-11-13 的回答：帳冊不變；綱要有兩層，文章層每節一句、段落層每段至少一句；每一句是段內的一個要點；兩種起點（寫完的稿、從零開始）都要；整份確認與一節一節確認都要支援。另一個工作階段正在替一篇真實的數學稿件手排綱要，它用到的欄位也拿來核對過這份設計。

限制：

- Swift 規則：新的檢查與新的測試都要寫成 Swift，而 repo 還沒有 Swift package（#46）。這個 change 因此沒有新的可執行程式，也沒有新的測試。
- 「plan」在 plugin 裡已經有兩個意思（結構附檔的節計畫與段計畫、承諾種類 plan），新的檔案叫綱要（outline）。
- analyze 的七個狀態由規格與測試釘住，不動。

## Goals / Non-Goals

**Goals:**

- 有地方放還沒寫的內容：每節一句、每段至少一句要點。
- 從寫完的稿反推出來的綱要，每一筆都對得回原稿；作者合併、搬動、刪除之後仍然對得回。
- 動筆之前有一道作者的確認；確認之後改過的部分看得出來，只需要重新確認受影響的節。
- 還沒採用帳冊的稿件也能用。

**Non-Goals:**

- 照綱要把文字寫進稿件、記下哪段文字來自哪一句、比對寫出來的段落有沒有說到那一句。這是 #51，要先有 #49 的寫入流程。
- 綱要檔的機械檢查與測試。這是 #78，要先有 #46 的 Swift package。
- 修改帳冊的 schema、結構附檔、義務表、analyze 或任何既有腳本。
- 每一句要點的證據狀態詞彙。寫出來拆成命題之後，帳冊的 evidence_class 會記。
- 全文層級的限制（例如「哪些說法不得再出現」）與各節的長度加總。它們不屬於任何一節或一段，這一版沒有地方放。
- 把「段落有沒有說到綱要的那一句」列進義務表。義務表的單位只有命題與整篇文章；綱要是寫作過程的計畫，不是文章欠讀者的東西。

## Decisions

### 綱要分成三個檔，放在帳冊旁

outline-sections.jsonl 是文章層，一節一筆；outline-paragraphs.jsonl 是段落層，一段一筆；outline-approvals.jsonl 是確認紀錄，一筆一次確認。三個檔都在帳冊的目錄裡，比照驗證紀錄的做法：放在旁邊、不改帳冊。

為什麼不是一個檔放兩種紀錄：維護者要的是「段落這一層有自己的 JSONL，一段一筆」，文章層另外一個。為什麼確認紀錄不寫進綱要檔：綱要會一直改，確認紀錄只增不改，兩者分開才看得出「通過時是什麼」。

目錄裡可以只有這三個檔而沒有帳冊，所以還沒拆成命題的稿件也能用。

### 段落紀錄以要點為單位，至少一句

一筆段落紀錄有自己的 id、所屬的節，以及一到多個要點；每個要點有自己的 id 與一句完整的句子。只有一個要點時，它就是這一段的主旨句。要點有自己的 id，是因為之後的擴寫與比對（#51）要能指到單獨一句。

要點可以帶 basis（撐住這一句的東西在哪裡）與 pending（作者還要補什麼）。起草時作者沒給的結果、數字、引用，寫成「這裡會報告什麼」並標上 pending，不編造。

原樣搬動的區塊（定理的陳述、證明、圖、表、推導）也是一筆，標上 carry；它的要點只說明這個區塊是什麼，不擴寫。這類區塊在數學稿件裡數量很大，不該逼人替每一個寫要點句以外的東西。

沒有採用的做法：一句綱要對一整段（維護者選了「段內的一個要點句」）；替區塊另立一組種類詞彙（carry 一個標記就夠，種類可以寫在說明裡）。

### 來源用 label 或開頭文字指回原稿

來源指標是一個物件：檔名，加上 LaTeX 的 label 或那段文字開頭的幾個字，兩者至少一個。行號可以寫，但只有同時寫了 commit 才可以。真實稿件的經驗是行號在一天之內就因為別的修改全部失效，所以行號只當出處，定位靠 label 或文字。

檔名可以指到稿件以外的檔（例如 repo 裡的筆記），所以新增的段落也能記它的依據。要點的 basis 用同一種指標。

沒有採用的做法：記原稿每個檔的指紋（要在檔案開頭多一筆不是節也不是段的紀錄）；只記行號。

### 修改時不丟來源，刪除是標記

合併兩筆時，新的那一筆的來源是兩筆來源的聯集。拆開一筆時，原本的每一個來源至少留在其中一筆。有來源的一筆被刪除時，那一筆不拿掉，而是標上 dropped 並寫理由；沒有來源的一筆可以直接拿掉。

這樣「原稿的每一段去了哪裡」永遠可以從來源反查，不需要另外維護一張對照表；被刪除的每一筆在確認時也會連同理由給作者看。

### 確認紀錄存下通過當時的內容，以節為單位

一筆確認紀錄存下：時間、作者當時說的話、涵蓋的每一節當時的紀錄與那一節所有段落當時的紀錄（照順序）。涵蓋所有節的那一筆另外標成整份確認，它同時記下了節的順序。

一節「仍照通過時的內容」的條件：最近一次涵蓋它的確認紀錄裡，存下的那一節與現在的相同，存下的段落與現在的逐筆相同、順序相同。「相同」是指 JSON 的值相同，鍵的順序不算。節的順序則看最近一次整份確認。

為什麼不用指紋：重新確認時要給作者看差異，那需要通過當時的文字；既然文字存下來了，指紋與它的正規化規則就不需要。為什麼以節為單位：維護者要整份與一節一節兩種方式，而一段的順序、增刪只有在它所在的節裡才看得出來。只改一句話時重新確認的仍是那一節，但呈現給作者的只有差異。

不讓工具判斷改動是不是「實質」的：任何不同都要重新確認，代價是改一個字也要再看一次差異。

### 只有作者當次明說才算確認

照維護者的審稿 plugin 的做法：skill 把綱要給作者看之後停下來；作者在回覆的那一則訊息裡明說通過，才寫確認紀錄。不算的情況是封閉的五種：綱要還沒出現之前給的概括指示、由另一個 agent 或工作階段轉述的同意、對較早版本或別的節的同意、沒有回覆或回覆的是別的事、叫另一個 skill 開始寫。

預設給作者看整份並請他確認整份；作者點名某幾節時才只確認那幾節。

### 前提檢查由另一個 agent 做，結果只呈現不改綱要

給作者確認之前，把要確認的紀錄交給另一個 agent。它只拿到綱要檔與來源指標指到的檔案，看不到對話。它回報的是封閉的六種：不是句子、來源不支持、沒有東西可以對照、用到後面才出現的東西、節的那一句沒有被它的段落撐住、來源指標解析不到。

結果連同它指到的那一筆一起給作者看。skill 不因為檢查結果自己改綱要：綱要是作者的計畫，改不改由作者決定。這和審稿 plugin 不同（它會先把站不住的條目改掉），原因是審稿的大綱是模型寫的，而綱要在作者修改之後是作者的。

### 沒有列出的鍵原樣保留

節與段落的紀錄、要點、來源指標裡，規格沒有定義的鍵都允許存在。skill 改寫一筆時原樣保留它們，不解讀。真實稿件已經需要長度目標、待決的版本這類欄位；先讓它們放得進去，等用法穩定再決定要不要寫進規格。確認紀錄的鍵是封閉的。

### skill 只寫三個綱要檔

/propositions:outline 不寫稿件、帳冊、結構附檔與驗證紀錄，也不改寫或刪除已有的確認紀錄。反推與起草的結果先給作者看，作者同意才寫進稿件的 repo；已經有綱要檔時不覆蓋。每次寫入之後用 jq 確認每一行是 JSON 物件、id 沒有重複，並在回報裡說明目前沒有其他格式檢查。

### 機械檢查與測試留給 #78

每一條 requirement 都寫一行沒有可執行檢查的理由，指到 #78。這個 change 的驗收靠獨立讀者盲驗：讀者只拿到說明文件與題目，判定幾份綱要檔合不合格式、哪些節仍照通過時的內容。

## Implementation Contract

**交付的行為**

- 說明文件寫明三個檔的每一個鍵、來源指標、確認紀錄，以及「一節仍照通過時的內容」「節的順序仍照通過時的順序」「綱要仍照通過時的內容」三個判定。只讀這份文件的人，拿到三個檔就能判定每一節的狀態。
- skill 有六個動作：反推、起草、修改、前提檢查、確認、狀態。每個動作讀什麼、寫什麼、什麼時候停下來等作者，都寫在 skill 裡，並和規格一致。
- skill 的文字裡沒有交給直譯器執行的程式本體（沒有 heredoc 的 Python 或 shell 程式）；只有呼叫現成工具的指令列。

**資料形狀**

- 節：id、heading、says 必填；role、parent、dropped 選填。
- 段落：id、section、points 必填（points 至少一個，每個有 id 與 text）；from、carry、uses、dropped、note 選填；要點另可有 basis、pending。
- 來源指標：file 必填；label 與 starts 至少一個；lines 只和 commit 一起出現。
- 確認紀錄：approved_at、statement、sections 必填；whole 選填。

**失敗的情況**

- 已經有綱要檔時，反推與起草停下並說明，不覆蓋。
- 作者的回覆不是當次明說的同意時，不寫確認紀錄，並說明還缺什麼。
- 寫入之後 jq 發現某一行不是 JSON 物件或 id 重複時，回報是哪一行，不宣稱寫入成功。

**驗收**

- 獨立讀者盲驗：題目涵蓋格式（必填的鍵、來源指標的四種寫法、原樣搬動、刪除的標記）、三個判定（改一句、搬一段、加一節、只改鍵的順序、重新排列段落）、什麼算確認（五種不算的情況）。讀者的答案與預先存好的答案全部相同。
- 既有的測試全部通過，沒有新增測試檔。
- spectra validate 與 spec-change 的連結檢查通過。

**範圍**

- 在範圍內：規格 article-outline、說明文件、skill、三份說明文件與 schema 文件的清單、版本號。
- 不在範圍內：任何腳本、任何既有規格、義務表、analyze、construct、#51 與 #52 的正文。

## Risks / Trade-offs

- [沒有機械檢查，格式會走樣] → skill 每次寫入後用 jq 做兩項最基本的確認，並在回報裡明說沒有其他檢查；#78 補上。
- [規格的每一條都沒有可執行的檢查] → 規範句盡量少，清單都寫成封閉的；用獨立讀者盲驗代替；#78 逐條補範例與測試。
- [以節為單位，改一個字也要重新確認那一節] → 重新確認時只呈現差異，作者看一眼就能通過。
- [開頭文字在原稿被改掉之後找不到] → 前提檢查會回報解析不到的來源指標；同時有 label 時以 label 為準。
- [沒有列出的鍵各稿件自己用，之後可能彼此不相容] → 這一版只保證保留不解讀；哪些要收進規格等有兩篇以上的稿件用過再決定。
- [反推時段落的切分沒有機械的結果可以對照] → 作者會讀整份綱要；有帳冊的單檔稿件之後可以用既有的段落清單對照（#77 處理多檔）。

## Migration Plan

純新增。沒有既有的檔案要轉換；不裝新版 plugin 的人不受影響。要撤回時把三個綱要檔留在稿件的 repo 也不會影響任何既有的檢查。
