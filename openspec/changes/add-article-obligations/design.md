## Goals / Non-Goals

**Goals:**

- 「完全合理」有一份定義，後面的工具與 skill 都照它算。
- 分得出哪些列在檢查帳冊與附檔，哪些列在檢查文章。
- 每一列都指得到一個已實作的檢查，或一張負責補上它的 issue。
- 四種結果的規則寫到另一個讀者照著做會得到同樣的答案。
- 檢查或詞彙增加而表沒有跟著改時，測試會失敗。

**Non-Goals:**

- 不寫照表算出結果的工具。那要等 #46 的 package，報告由 #54 做。
- 不補任何缺口的檢查。
- 不改驗證紀錄的格式。讓紀錄指到某一列是另一張 issue。
- 不定佔位的寫法（#49），不新增公理（#48）。
- 不改 `proofread`、`construct` 或其他 skill 的流程，也不讓它們讀這張表。

## Decisions

### 一列一條義務，存成資料檔加說明文件

表存成 `plugins/propositions/catalog/obligations.yaml`，比照同目錄的詞彙檔；說明寫在 `plugins/propositions/docs/OBLIGATIONS.md`。一列是一條要成立的事，附上它適用的條件。

不採一列一種特性：很多條跨好幾種特性，例如引用方向對每一筆有引用的命題都適用，照特性排要在十幾列各寫一次。不採只有 markdown：#46、#49、#50、#54 都要逐列讀這張表。

各列的編號是「前綴加短名」，例如 `dependence.cites-backward`，不用單一字母開頭，免得和 R、S、L、E、V 混淆。

### 類別只有前提與義務

- **前提**：沒過時要改的是帳冊、附檔或驗證紀錄。它沒過，表示索引不可信，文章的結果還不能看。
- **義務**：沒過時要改的是稿件，或要作者做決定。

類別逐列寫在檔案裡，不從「哪個工具驗的」推導。一條檢查兩種都有時拆成兩列、指向同一條檢查：S5 的「主旨有寫出來」是義務，「章節與段落的欄位齊全」是前提。編號的前綴跟著類別：前提用 `index`，義務用所屬的組。

同一條檢查拆成多列時，它的一個發現算在哪一列，看那個發現違反的是哪一列的判準。這要靠讀的人判斷；之後的工具要讓檢查回報到列，這裡不處理。

只報資訊的發現不另立類別。維護者看過、定為只是資訊的有兩個：交叉弧（S7）與孤立命題（R3 的警告）。它們各佔一列，類別照「真的要改時改哪裡」定，警告欄寫只是資訊（見「警告由每一列寫明」）。考慮過另立第三類「資訊」，沒有採用：維護者在 #47 定的是兩類，而且這些發現真要處理時，改的都是帳冊或附檔，放在前提說得通。#47 的決定紀錄（comment 6792376873）在「留給 proposal 的細節」寫過這類規則「不算前提也不算義務」，這裡的做法和那句話不同，那則紀錄會跟著更正。

章節沒有命題（R1.5）不在那兩個裡面。驗證器把它標成資訊，但維護者沒有看過這一列，而且覆蓋檢查只看抽取過的範圍，R1.5 是唯一看得出整節沒有抽取的訊號。它先寫要判定，在審表的停點由維護者決定。

### 義務依原則分七組，一組對一條公理

| 組 | 保護什麼 | 公理 |
|---|---|---|
| `dependence` 依賴 | 每一句只依賴前面已經出現的東西 | `academic-writing/A1_no_forward_dependence` |
| `commitment` 承諾 | 對讀者開出的承諾都有兌現 | #48 新增 |
| `support` 支持 | 每個主張都由它的依據撐得起來 | #48 新增 |
| `consistency` 一致 | 前後說法不衝突 | #48 新增 |
| `truth` 真實與來源 | 內容為真，數字與引用查得到來源 | #48 新增 |
| `placement` 位置 | 內容放在該放的章節 | #48 新增 |
| `completeness` 完成 | 稿件沒有留下沒寫完的地方 | 可能沒有 |

每一組在檔案裡有一句英文說明它保護什麼，以及公理的編號。表不重抄公理的內容。一組最多一條公理；這個 change 只填「依賴」那一條，其餘的欄位先不寫，等 #48。

不採照「誰來驗」分組：同一個原則會散在機械、模型、外部工具三組，#48 要新增哪些公理也沒有對照。

### 適用條件只用欄位值的清單

`applies` 是一個對照表，鍵只能是 `profile`、`claim_type`、`evidence_class`、`cites`、`opens`、`section_role`，值是允許的值的清單。一筆命題要每個鍵都符合才算適用；沒有 `applies` 的列對每一筆都適用。`cites` 的值只有 `present` 與 `absent`。以整篇文章為單位的列只能用 `profile`。

不做運算式，也沒有「或」與「非」。需要「或」的拆成兩列。理由是這個檔案要能用很少的規則檢查，不在資料檔裡發明一種小語言。

鍵只收這六個。`move`、段落類型、`relation` 這三個欄位在附檔裡是選填的，拿來當適用條件，沒標的命題會被默默當成不適用；目前也沒有哪一列需要它們。之後有列需要時再加鍵。

`proofread` 的 E 層（E1 到 E7 的列與 E8 到 E10 的缺口）一律只適用實證 profile 的帳冊：那一套閱讀用到的詞彙只有實證 profile 接受。沒有這一條，數學稿的每一筆命題在 E 層都會是沒檢查，永遠過不了。L 層不綁 profile：技能文件寫的是看主張靠什麼成立來選閱讀方式，混合稿件兩種都跑，所以 L 層各列適用哪些命題在寫表時逐列定，並在審表的停點給維護者看。

每個詞彙值都要有交代：`claim_type`、`evidence_class`、承諾種類、章節角色這四個欄位的每一個值，要嘛被至少一列的 `applies` 點名，要嘛列在檔案的 `unconstrained` 清單裡並寫一句原因。

### 檢查欄只填已實作的檢查，其餘標成缺口並指到 issue

`check` 的值是清單裡的一個編號，或 `gap`。編號帶來源，因為有兩套 R：帳冊驗證器的寫 `ledger:R2`，跨檔案稽核的寫 `audit:R2`。清單是 Context 那 44 條，寫法是 `ledger:`、`structure:`、`records:`、`audit:`、`proofread:` 加編號，以及沒有編號的兩條 `coverage:text` 與 `order:ledger`。清單以規格列的為準；「會留下可以讀的發現或紀錄、而且不改檔案」是說明它為什麼這樣列。

沒有列入的，與原因：

- 跨檔案稽核的第四項：它就是帳冊驗證器。
- 定理環境的邊界稽核、行號重新定位的試跑：分別和 R9、R13 是同一個檢查。
- 連結目錄的現況檢查：對象是 plugin 自己的檔案，不是稿件。
- `tschema-check`：在另一個 plugin，歸 #50。
- `clarity-audit` 的九類讀者卡點：它產出的是改寫，不對每一筆命題留下判定。其中幾類對應到依賴、支持、真實這幾組的義務；那些義務在表裡指向別的檢查，或標成缺口。
- `construct` 摘要裡的計數、`analyze` 判斷狀態的表：是流程裡的步驟，沒有可以引用的編號，也不留紀錄。
- `proofread` 的 E8 到 E10：層級表有定義，逐筆流程沒有列，所以一筆判定不保證它們看過。

既有的 Python 不能再加檢查規則，所以這份清單在 Python 這邊是封閉的。之後實作新檢查的 change（例如 #46）要在同一個 change 裡把編號加進清單與測試，並把那一列從 `gap` 改成編號。

`gap` 的列必須有 `owner`，寫負責補上它的 issue 號。目前知道的缺口：

| 缺口 | 負責的 issue |
|---|---|
| 引用只指向前面 | #46 |
| 符號先被引入 | #55 |
| E8、E9、E10（三列） | #57 |
| 文獻查得到 | #50 |
| 稿件沒有佔位 | #49 |
| 章節角色的兩條 | #60 |
| 一般性的矛盾 | #61 |

`order:ledger` 是已實作的檢查，但它的工具只支援單檔稿件。多檔稿件的那一列因此只能是沒檢查，負責補上的是 #59。這不是缺口（檢查存在），所以那一列的 `check` 仍然是 `order:ledger`、沒有 `owner`；限制寫在說明文件。

### 驗證方式與四種結果

`verified_by` 寫這一列靠什麼驗：`mechanical`，或一個以上的驗證方法（`proofread`、`cross_model`、`lean` 這些，詞彙取自 `plugins/propositions/docs/VERIFICATION.md`）。列出的方法全部都要。

凡是列了 `proofread` 的列，都要同時列 `cross_model`。#45 的驗收寫的是「靠模型判斷的條目由另一個模型複查」，而 `proofread` 的每一層都是模型在讀，包括技能文件標成大致可機械化的那幾層。所以這裡不挑層，全部要第二次閱讀。

一列對一筆命題（或整篇文章）的結果，依序判定，先符合的為準：

1. 不符合 `applies`：**不適用**。
2. `check` 是 `gap`：**沒檢查**。
3. `mechanical`：檢查沒有對目前的檔案跑過是**沒檢查**；報錯誤是**沒通過**；報了不算錯誤的發現時照下一節的警告欄；沒有任何發現是**通過**。嚴重度照工具自己的標示：驗證器的錯誤、稽核腳本的 `definite`、覆蓋檢查回報的漏掉的文字、行序試跑回報要搬動的行，算「錯誤」；驗證器的警告、稽核腳本的 `likely` 與 `FYI`、行序試跑回報的同一行多筆命題，算「不算錯誤的發現」。不指名任何單位的狀態行與摘要不算發現。不用結束碼來分，因為三支稽核腳本只要有任何發現就以失敗結束。
4. 驗證方法：取每個方法對這筆命題最新的一筆判定。任何一筆是 `refuted` 或 `partial` 就是**沒通過**；全部是 `supported`、而且每一筆都涵蓋這一列的檢查，是**通過**；其餘是**沒檢查**。

紀錄只記命題與方法，指不到是哪一列，所以兩個方向分開處理，都往不放行的方向取：

- 沒過的判定往寬算：一筆 `refuted` 或 `partial` 會讓同一筆命題上由那個方法驗的列全部沒通過，不論它屬於前提還是義務。代價是報告分不出該改帳冊還是改稿件，要回去看 `proofread` 的發現紀錄。
- 通過的判定往窄算：一筆 `supported` 只對那次閱讀實際做過的檢查算數。`proofread` 有兩種閱讀，推導的那一種走 L 層，實證的那一種走 E 層，流程互不包含；紀錄沒有記是哪一種，只能從 `evidence_ref` 指到的清單看出來。看不出來的紀錄不涵蓋任何一層。少了這一條，一筆實證閱讀的 `supported` 會把沒走過的 L 層一起算成通過。

| 情況 | 結果 |
|---|---|
| 數字與產物一致（`proofread:E1`，只適用實證稿）對一篇數學稿的 `claim` | 不適用 |
| `dependence.cites-backward`（缺口）對一筆有引用的命題 | 沒檢查 |
| 同一列對一筆沒有引用的命題 | 不適用 |
| `structure:S6` 的列（要判定），S6 對那個預告報了警告 | 沒檢查 |
| `structure:S6` 的列，驗證器跑過、S6 對它沒有任何發現 | 通過 |
| `structure:S7` 的列（只是資訊），兩條弧交叉 | 通過，發現列為資訊 |
| `proofread:L4` 的列，有推導閱讀的 `proofread` `supported`、沒有 `cross_model` 的紀錄 | 沒檢查 |
| `proofread:L4` 的列，兩種方法都是 `supported`，但 `proofread` 那一筆的清單是實證閱讀 | 沒檢查 |
| 同一筆命題的 `proofread` 是 `partial` | `proofread:L1` 與 `proofread:L4` 的列都沒通過 |
| `proofread` 是 `supported`、`cross_model` 是 `refuted` | 沒通過 |

### 警告由每一列寫明

以 `mechanical` 驗的每一列都有一欄 `on_warning`，值是 `judge` 或 `info`，沒有第三個值，也不能省略：

- `judge`：檢查報了不算錯誤的發現時，要有人判定，判定之前算沒檢查。
- `info`：那種發現只列在報告，這一列算通過。

這是維護者在 #47 選的做法：不寫一句總括的判準，逐列寫明。他看過的四個例子：引用只指向前面與 S6 是 `judge`，S7 與孤立命題是 `info`。不會報警告的檢查也寫 `judge`，這樣檢查日後開始報警告時，預設是要判定而不是放行。

每一種不算錯誤的發現在表裡剛好有一列。一條檢查的警告和它的錯誤講的是同一件事時共用一列；講的是另一件事時（R3 的孤立命題、S4 的 `setup`、稽核腳本的 `FYI`）另開一列，這樣發現算在哪一列不必靠猜。

`info` 只能出現在維護者看過的列。守衛測試存著這些列的檢查編號，一開始是 `structure:S7` 與 `ledger:R3`；維護者在審表時再定別的列只是資訊，就在同一個 change 把它的檢查編號加進去。

現在沒有地方記錄「某一列的警告已經判定過」，所以報了警告的 `judge` 列會一直是沒檢查。補上這條路徑要改驗證紀錄的格式，由這個 change 開的 issue 負責。

### 驗收是每一條都通過，現在沒有文章過得了

一篇文章完全合理，是指每一列、對每一筆命題與整篇文章，結果都是通過或不適用。只要有前提沒過或沒檢查，義務的結果就標成不可信，先修索引。

現在沒有任何文章過得了，原因有三個，各有負責的 issue：

1. 有缺口的列。每一列自己寫了負責的 issue。
2. 驗證紀錄說不出它涵蓋什麼：`judge` 的警告沒有地方記錄判定，`proofread` 的紀錄也沒有記是哪一種閱讀。#62。
3. `cross_model` 還沒有產生紀錄的工具。#21。

多檔稿件另外有一列過不了：行序的檢查只支援單檔稿件（#59）。

說明文件要把這三點與多檔稿件的限制寫出來。只說「有缺口」會讓人以為補完缺口就過得了。

### 說明文件不重抄各列

`plugins/propositions/docs/OBLIGATIONS.md` 講九件事：資料檔的鍵、兩種類別與怎麼分、分組與公理、適用條件、哪些檢查算已實作、四種結果、驗收、過不了的三個原因、怎麼新增或修改一列。它不列出各列，最多拿兩個編號當例子。各列只存在資料檔，免得兩份清單各改各的。

### 守衛測試加在既有的 pytest 檔

Swift 規則要新的測試用 Swift Testing，但 repo 還沒有 package。#40 的做法是把只釘住文字的測試加進 `tests/test_plugin_payload_tracked.py`。這次的測試走得比那次遠：要解析資料檔、檢查跨欄位的限制，並從兩個驗證器讀出詞彙。維護者在 #47 定了「先靠測試守住格式與完整性」，所以照做，但守三條界線：不新建測試檔；不新增腳本或 `_lib` 模組，解析在測試裡用 PyYAML 完成；沒有 PyYAML 時只跳過這幾個案例，和另外兩個用到它的測試檔一致。驗收時這組案例必須是通過，不能是跳過。

## Risks / Trade-offs

- [表變成第二份規格] → `criterion` 限一行、200 字元以內，只寫要成立的事；檢查的定義留在原來的文件；說明文件不列各列。
- [把還沒有的檢查寫成有] → 清單是封閉的，測試拒絕清單外的編號。#55 與 #57 就是文件寫了、流程沒做的例子。
- [現在沒有文章過得了，定義看起來沒有用] → 報告說得出是哪幾列、哪一張 issue；每補一個缺口就少一列。
- [一筆 `partial` 讓同一種方法驗的列全部沒通過] → 寧可多報沒通過。讓紀錄指到某一列由新開的 issue 處理。
- [`proofread` 的紀錄看不出是哪一種閱讀時，它驗的列全部是沒檢查] → 寧可多報沒檢查。讓紀錄記下閱讀方式由新開的 issue 處理。
- [同一條檢查拆成多列時，發現算在哪一列要靠判斷] → 判準一句話寫清楚；獨立讀者盲驗裡放一題這種情況。
- [`proofread` 驗的列全部要第二次閱讀，成本高] → 這是照驗收的保守讀法。哪幾層可以免，列在 Open Questions。
- [多檔稿件的行序沒有檢查，結構檢查的結果沒有依據] → 那一列照規則是沒檢查，不會被算成通過；#59 負責補上。
- [守衛寫在 Python，和 Swift 規則的方向相反] → 不新增檔案與模組，並寫明退場條件。
- [各列的類別是判斷，可能分錯] → 維護者審表的停點，加上獨立讀者盲驗。
- [表在 #46、#49 用到它之前沒有人讀，可能過時] → 完整性的兩個條件由測試守著，詞彙或清單一變就會失敗。
