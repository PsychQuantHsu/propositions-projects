# Construct — the article as a whole

The ledger says what each proposition claims. This skill adds how the article is built, in
three layers that together decide what the next proposition should do (format 2.0 and
vocabularies: `docs/STRUCTURE.md` in this plugin; decision procedure:
`references/vocabulary.md`):

| Layer | Question | Where it is recorded |
|---|---|---|
| Commitments | What has the article promised the reader, and has it kept it? | `discourse.jsonl`: `opens`, `discharges` |
| Section roles | What is the current section for? | `structure.json`: `sections[].role` |
| Dependency tree | What does this proposition hang on inside its paragraph, and how? What does this paragraph hang on? Which section is this one under? | `discourse.jsonl`: `head`, `relation`, `also`; `structure.json`: `paragraphs`, `sections[].parent` |

Beside these layers, `move` on a record says what the sentence does for its paragraph, and
`type` on a paragraph says what the paragraph as a whole does. The values are in
`catalog/vocabulary.yaml` of this plugin. Explain mode prints them together with `head` and
`relation`, so that the relation between sentences can be read. A tool reads the vocabulary
only when a sidecar has one of these fields; it needs PyYAML for that, and without it the tool
exits 2 and names PyYAML.

`catalog/links.csv` is generated by `build-link-catalog.py` from annotated sidecars. It lists
every kind of link observed between moves (next sentence, head, `also`, citation, discharge of a
commitment, paragraph head), with counts. These are not rules: a link it lacks is not a problem.
Next mode reads its `next` links as a hint (N4); annotate and explain modes do not depend on it.

Labelling is a judgment task, so the model does it. Everything around the judgment is
mechanical:

| Risk | Gate |
|------|------|
| A sidecar skips, repeats or reorders propositions | S1 (`validate-structure.py`) |
| A label outside the closed vocabularies | S2, S3, S5 reject it; nothing is mapped to a near value |
| A head outside its paragraph, two roots, a cycle, a paragraph across a section boundary | S2, S5 |
| A promise kept before it was made, or never kept | S3, S4 |
| An announcement kept far from where it was made | S6 (warning) |
| Crossing arcs (the text is not tree-shaped there, or a head was chosen badly) | S7 (warning) |
| A `basis` edge the ledger does not cite | S8 (warning): fix the ledger's `cites`, not the relation |
| A `move` or paragraph `type` outside `catalog/vocabulary.yaml` | S9 rejects it; no order of moves is ever reported |
| A record with no `move`, or a paragraph with no `type` | S9 allows it because both fields are optional, so the A5 summary counts them; annotate mode must bring both counts to 0 |
| A half-finished annotation lands in the ledger directory | all drafting happens in a staging directory; the ledger directory changes only after the validator passes and the user confirms |
| The skill alters the ledger | outside write mode it never writes `main.jsonl`, and its sha256 is compared before and after; write mode writes the manuscript, the ledger and the sidecars only through `propositions write commit`, after the author confirms |

## Resolve scripts and paths

```bash
PLUGIN_ROOT="${CLAUDE_PLUGIN_ROOT:-$(ls -d "$HOME"/.claude/plugins/cache/propositions-projects/propositions/*/ 2>/dev/null | sort -V | tail -1)}"
SCRIPTS="$PLUGIN_ROOT/scripts"
VALIDATOR="$SCRIPTS/validate-propositions.py"
COVERAGE="$SCRIPTS/check-extraction-coverage.py"
VSTRUCT="$SCRIPTS/validate-structure.py"
STATE="$SCRIPTS/structure-state.py"
METRICS="$SCRIPTS/structure-metrics.py"
MIGRATE="$SCRIPTS/migrate-structure-v2.py"
EXPLAIN="$SCRIPTS/structure-explain.py"
LINKS="$SCRIPTS/structure-links.py"
for f in "$VALIDATOR" "$COVERAGE" "$VSTRUCT" "$STATE" "$METRICS" "$MIGRATE" "$EXPLAIN" "$LINKS"; do [ -f "$f" ] || { echo "missing $f"; exit 2; }; done
```

Establish, from the request or by asking once (AskUserQuestion, all at once):

- `LEDGER` — the ledger directory (holds `main.jsonl` and `_meta.json`).
- `MAIN` — the manuscript's main `.tex` file.
- The mode: **annotate** (the manuscript is written; label its structure), **next** (the user is
  writing; say what comes next), **write** (the user is writing; write the next paragraph into
  the draft, with its propositions and records, behind one confirmation) or **explain** (the
  sidecars exist; say how the sentences of a paragraph or section relate). "下一句" / "what
  next" means next; "寫進稿件" / "write the next paragraph" means write; "標註" / "check the
  structure" means annotate; "這段句子之間是什麼關係" / "explain how these sentences relate"
  means explain. When it is unclear whether the user wants a suggestion or a written paragraph,
  it is next mode: only write mode changes files.

If `LEDGER/_meta.json` is missing, the manuscript has no ledger: point to Operation D of
`/propositions:prop-ledger`, then `/propositions:prop-extract`.

Record the ledger's fingerprint before doing anything else; every exit path compares it:

```bash
LEDGER_SHA=$(shasum -a 256 "$LEDGER/main.jsonl" | cut -d' ' -f1)
```

## Annotate mode

### A1 — Preconditions: a valid ledger that covers the text

```bash
python3 "$VALIDATOR" --jsonl "$LEDGER/main.jsonl" --meta "$LEDGER/_meta.json" --tex "$MAIN"
```

Then run `check-extraction-coverage.py` over every line range the ledger is meant to cover
(the body from the first to the last extracted line of each file; ranges the ledger's
`_meta.json` coverage marks as excluded, such as appendices and declarations, stay excluded):

```bash
python3 "$COVERAGE" --tex "$FILE" --lines "$A-$B" --jsonl "$LEDGER/main.jsonl" --main "$MAIN"
```

If the validator exits non-zero or any range reports uncovered text, **stop**: report the
failures and send the user to `/propositions:prop-extract`. Structure laid over a ledger with gaps
would mislabel the propositions on both sides of each gap. Write nothing.

A ledger not in TeX reading order, or one of about 100 propositions or more, goes through
`/propositions:prop-construct-batch`, which replaces A3 and returns here at A4. So do sidecars whose
tree already exists and which lack only moves and types, at any length: its moves-only path
labels those two fields and leaves the tree alone.

### A2 — Read, and start from the paragraph plan

Read `references/vocabulary.md` and `catalog/vocabulary.yaml` of this plugin
(`$PLUGIN_ROOT/catalog/vocabulary.yaml`). Then read the manuscript and the ledger together in reading
order (the `main.jsonl` line order, retired propositions skipped). Note every sentence that
promises something (a question, an aim, a hypothesis, "organized as follows", "We now …"),
every sentence that keeps one, every heading that starts a section with its own text, and
which sections sit under which.

```bash
STAGE=$(mktemp -d "${TMPDIR:-/tmp}/construct-XXXXXX")
bash "$PLUGIN_ROOT/hooks/run-cli.sh" "${CLAUDE_PLUGIN_DATA}" paragraphs --jsonl="$LEDGER/main.jsonl" --tex="$MAIN" > "$STAGE/paragraphs.json"
```

`paragraphs.json` is the default paragraph plan (one entry per run of non-blank TeX lines; a
location may be in any file of the main file's `\input` tree). It is the `paragraphs` command of
the plugin's `propositions` tool, run through the launcher, which runs only the pinned binary.
Rerun it with `--structure="$STAGE/structure.json"` once the section list is drafted, so that
no paragraph crosses a section start. Merge or split entries only where a TeX paragraph makes
two arguments or two make one, and say so in the summary. Exit 2: show what it printed and stop.
Exit 3 (`propositions: NOT RUN`, the tool is not installed, for one on a system other than
macOS): list the paragraphs by hand, and say in the summary that no plan was derived.

If `LEDGER` holds **version 1.0** sidecars (`structure_version` `"1.0"`), convert them first
and start from the result; its review report lists what the mechanical conversion could not
decide:

```bash
python3 "$MIGRATE" --jsonl "$LEDGER/main.jsonl" --tex "$MAIN" --out-dir "$STAGE"
```

### A3 — Draft in staging

Write `$STAGE/discourse.jsonl` — one record per non-retired proposition, in ledger order — and
`$STAGE/structure.json` (`structure_version` `"2.0"`, thesis, sections with `parent`,
paragraphs). Follow `references/vocabulary.md`: per paragraph its root, then per proposition
its head (inside the paragraph, before or after it), its relation, what it opens and
discharges, any `also`, and its `move`; per paragraph after a section's first its head
paragraph and relation; every paragraph's `type`, once its sentences are labelled; per
subsection its `parent`. Put a `note` on every close call and nowhere else, written as
`runner-up: <the other choice>; lost because <reason>` (`references/vocabulary.md`, "Recording
the decision"). For a draft that has not stated its thesis yet, `thesis` is `[]`.

Every record gets a `move` and every paragraph a `type`, from `catalog/vocabulary.yaml`. A
needed value that is not in that file is a stop: report the sentence's position (or the
paragraph's id) and what it does, and never choose a near value.

If `LEDGER` already has version 2.0 sidecars, draft anyway; A5 shows the difference against them.
The exception is the moves-only path named in A1, which keeps the tree it finds.

### A4 — Validate the staged files

```bash
python3 "$VSTRUCT" --jsonl "$LEDGER/main.jsonl" \
  --structure "$STAGE/structure.json" --discourse "$STAGE/discourse.jsonl"
```

Add `--partial` only when the manuscript is unfinished, and say so in the summary. Fix the
staged files and rerun until the exit code is 0. Look at every S7 warning: a crossing is
usually a head chosen one sentence too far; keep it only when the text really is not
tree-shaped there, with a `note`. An S8 warning means the ledger lacks a `cites` entry; report
it so that the ledger is fixed (`/propositions:prop-extract` or a ledger edit), do not drop `basis`. An S4 error means a promise the article
never keeps: check the manuscript before deciding — either a discharge was missed, or the
article really leaves it open (say so in the summary; do not delete the commitment to make
the validator pass). A needed value that is not in the vocabularies is a stop: report it to
the user. The relation, commitment and role vocabularies change only through a spec change.
Moves and paragraph types change by editing `catalog/vocabulary.yaml` and passing its tests;
that is the maintainer's decision and not a step of annotating. An S9 error is one of these
stops unless the value is a typo of a listed id.

### A5 — Summary for the user

```bash
python3 - "$LEDGER/main.jsonl" "$STAGE" <<'PY'
import collections, json, sys
from pathlib import Path
ledger, stage = Path(sys.argv[1]), Path(sys.argv[2])
live = [p["id"] for p in map(json.loads, filter(str.strip, ledger.read_text().splitlines())) if "retired" not in p]
pos = {pid: i for i, pid in enumerate(live, 1)}
recs = [json.loads(l) for l in (stage / "discourse.jsonl").read_text().splitlines() if l.strip()]
print("relations:", dict(collections.Counter(r["relation"] for r in recs if "relation" in r).most_common()))
print("moves:", dict(collections.Counter(r["move"] for r in recs if "move" in r).most_common()),
      " without a move:", sum("move" not in r for r in recs))
heads = [(pos[r["prop_id"]], pos.get(r["head"])) for r in recs if r.get("head") not in (None, "pending")]
print("heads: before", sum(h < p for p, h in heads), "after", sum(h > p for p, h in heads),
      "roots", sum("head" not in r for r in recs), "pending", sum(r.get("head") == "pending" for r in recs))
opened = {}
for r in recs:
    for c in r.get("opens", []):
        opened[c["id"]] = [c["kind"], pos[r["prop_id"]], []]
for r in recs:
    for cid in r.get("discharges", []):
        opened[cid][2].append(pos[r["prop_id"]])
print("commitments:")
for cid, (kind, at, kept) in opened.items():
    print(f"  {cid:28} {kind:13} opened #{at:<4} kept {['#%d' % k for k in kept] or 'never'}")
st = json.loads((stage / "structure.json").read_text())
print("sections:")
for s in st["sections"]:
    print(f"  #{pos[s['first_prop']]:<4} {s['role']:13} {s['heading']}" + (f"  (under {s['parent']})" if s.get("parent") else ""))
print("paragraphs:", len(st["paragraphs"]), " with a head:", sum("head" in p for p in st["paragraphs"]))
print("paragraph types:", dict(collections.Counter(p["type"] for p in st["paragraphs"] if "type" in p).most_common()),
      " without a type:", sum("type" not in p for p in st["paragraphs"]))
print("thesis:", [f"#{pos[t]}" for t in st["thesis"]])
print("notes:", sum(1 for r in recs if r.get("note")))
PY
```

`without a move` and `without a type` must both be 0: S9 does not require the fields, so this
line is the check. If either is not 0, label the missing ones and go back to A4.

Then the warnings and the frontier length:

```bash
python3 "$VSTRUCT" --jsonl "$LEDGER/main.jsonl" --structure "$STAGE/structure.json" \
  --discourse "$STAGE/discourse.jsonl" | grep -E '^\[(WARN)\] S[78]|^  \[S[78]\]'
python3 "$METRICS" --jsonl "$LEDGER/main.jsonl" --structure "$STAGE/structure.json" \
  --discourse "$STAGE/discourse.jsonl" | grep -E 'frontier|crossing'
```

Show this output (every S7 and S8 warning, and the median right-frontier length), the list of
close calls (records with a `note`), and, when `LEDGER` already has sidecars, `diff` against
them. Say where the staged files are.

### A6 — Write only after confirmation

Ask (AskUserQuestion) whether to write the staged sidecars into `LEDGER`. If the user
declines, stop: nothing in `LEDGER` changes and the staged files stay in `$STAGE`. If the
user confirms:

```bash
cp "$STAGE/structure.json" "$STAGE/discourse.jsonl" "$LEDGER/"
python3 "$VSTRUCT" --jsonl "$LEDGER/main.jsonl"        # add --partial for a draft
[ "$(shasum -a 256 "$LEDGER/main.jsonl" | cut -d' ' -f1)" = "$LEDGER_SHA" ] || echo "main.jsonl CHANGED — stop and report"
```

## Next mode

### N1 — Preconditions: structure for the text written so far

The ledger must pass the validator and its sidecars must pass:

```bash
python3 "$VSTRUCT" --jsonl "$LEDGER/main.jsonl" --partial
```

If the sidecars are missing or fail, run annotate mode on the text written so far first
(with `--partial`), then come back. Fingerprint every file this mode must leave alone:

```bash
BEFORE=$(shasum -a 256 "$MAIN" "$LEDGER/main.jsonl" "$LEDGER/structure.json" "$LEDGER/discourse.jsonl")
```

### N2 — State at the end of the draft

```bash
python3 "$STATE" --jsonl "$LEDGER/main.jsonl" --at end --format json
```

It gives the current section and its role, the current paragraph and its root, the last
proposition's relation, the **right frontier** (the propositions, paragraphs and sections the
next proposition can attach to), the **pending** records (clauses still waiting for their
head), the open commitments in order of urgency (announcement, hypothesis, plan, question,
aim, setup; earliest first within a kind), the future-work list, and whether the thesis has
been stated. Read the propositions on the sentence part of the frontier as well.

### N3 — Say what the next proposition owes

Report, in this order: the current section and its role; the paragraph and its root; the
right frontier; the pending records; the open commitments as the state query ranks them.
Then the default answer:

1. If records are pending, the next proposition is their head (it completes the sentence they
   open).
2. Otherwise it advances the first open commitment, unless the section's role rules it out (a
   `discussion` does not open a new hypothesis except as `future_work`; `method` does not
   interpret results).
3. It attaches to a sentence node of the frontier, or starts a new paragraph when the
   paragraph's line is finished (its head paragraph is then on the paragraph part of the
   frontier).

### N4 — Read the move hint

The link catalog shows which moves have followed the last proposition's move. Use the top-level
`position` field of the N2 output to read that move:

```bash
python3 "$LINKS" sentence --jsonl "$LEDGER/main.jsonl" --at <position> --no-text --format json
```

Then, with the `move` it reports:

```bash
python3 "$LINKS" catalog --from <move> --kind next --format json
```

Use neither `--type` nor `--label`: the counts get too small to read, and tables from other
manuscripts still help.

Add up the rows by `to`: each row of `seen` has a `to` and a `total`, and there is one row per
relation, so one move can fill several rows. The hint is up to three values with the highest
totals. A tie keeps the order in which the values first appear in the listing, and `END` counts as
a value. Report the values with their totals, and say that these are observed paths, not a rule.

`END` is not a move: it says paragraphs often end after this move, which supports a candidate that
starts a new paragraph. The hint describes what follows inside the paragraph, so it says nothing
about the move of such a candidate, and no candidate's **Does** is `END`.

The hint only informs the **Does** item below. It does not change the order of the candidates or
the rule for the first one, and it does not choose the relation, because the catalog showed no lift
for relations. A candidate's move can be outside the hint, and nothing warns about that.

Skip the hint, say why in one line and go on to N5 in exactly three cases: the proposition has no
`move`; the catalog lists no `next` path from that move; or either query exits non-zero.

### N5 — Propose at most three candidates

Each candidate states:

- **Attaches to**: the frontier node it hangs on (`#n`), or the pending records it heads, or
  "new paragraph" with the paragraph it hangs on.
- **Advances**: the commitment id it opens, keeps or moves forward, if any.
- **Joins by**: the relation to that head and the connective that would show it.
- **Is**: the expected `claim_type` (and `evidence_class` for an empirical ledger).
- **Does**: the expected `move`, a value from `catalog/vocabulary.yaml`. If no value fits, write
  `none fits` and what the proposition does; never choose a near value.
- **Sentence**: one draft sentence, marked as a suggestion.

If records are pending, the first candidate is their head. Otherwise, if an `announcement` is
open, the first candidate keeps it — or, when keeping it needs facts the draft has not stated
yet, lays those facts down and says which announcement it prepares (the worked example in
`docs/STRUCTURE.md` keeps an announcement after laying down the counts it is about). Never invent results, numbers or
citations in a draft sentence: write a placeholder such as `[result of the test]`.

### N6 — Leave every file untouched

```bash
AFTER=$(shasum -a 256 "$MAIN" "$LEDGER/main.jsonl" "$LEDGER/structure.json" "$LEDGER/discourse.jsonl")
[ "$BEFORE" = "$AFTER" ] || echo "a file changed in next mode — stop and report"
```

Next mode writes nothing: not the manuscript, not the ledger, not the sidecars. Adding the
chosen sentence to the manuscript is the author's act; afterwards `/propositions:prop-extract`
and annotate mode bring the ledger and sidecars up to date.

## Write mode

Write mode adds one paragraph at the end of the draft: after the paragraph that holds the last
live proposition in reading order. It writes four files, the manuscript file that gets the
paragraph, the ledger, `discourse.jsonl` and `structure.json`, and only through
`propositions write commit`, which writes nothing unless the files are as they were when the
copies were made and the copies differ from them only by a new paragraph. Everything is drafted
in those copies.

### W1 — Preconditions

The same as N1: the ledger passes the validator and the sidecars pass `--partial`. Then check
that the tool is there:

```bash
CLI=(bash "$PLUGIN_ROOT/hooks/run-cli.sh" "${CLAUDE_PLUGIN_DATA}")
"${CLI[@]}" write prepare --help > /dev/null
```

Exit 3 means the pinned tool is not installed (it is a macOS binary): say that write mode needs
it, offer next mode instead, and stop.

### W2 — Decide what the paragraph does

Run N2 to N5 for the first sentence of a new paragraph, or take the plan the author gives. Agree
with the author, in one question (AskUserQuestion), what the paragraph does: what it attaches
to, which commitments it advances, and its claims. A claim that changes what the paper argues is
the author's to make; when the author has not made it, write a placeholder for it.

Each example, definition or result comes after text that raises the question it answers: earlier
in the paragraph, or anywhere in the text before it (the obligation group `motivation`, axiom
`academic-writing/A2_motivated_by_prefix`; issue 139). When nothing before an example, a
definition or a result raises its question, write the sentence that raises it first, or tell the
author that nothing does (W8). No command checks this yet (issue 141).

Never invent a result, a number or a citation. Write each as a placeholder
`{PENDING: <what is to be supplied>}`. It needs no macro, compiles as it is and shows in the PDF.
A citation key may be used only when it is in the manuscript's bibliography file; any other
citation is a placeholder.

### W3 — Prepare the copies

```bash
STAGE=$(mktemp -d)/write
"${CLI[@]}" write prepare --jsonl "$LEDGER/main.jsonl" --tex "$MAIN" \
  --structure "$LEDGER/structure.json" --discourse "$LEDGER/discourse.jsonl" --stage "$STAGE"
```

It prints the line after which the paragraph goes and the path of each copy: the manuscript
file, the main file, the ledger, `structure.json` and `discourse.jsonl`. Every later step uses
those paths. Exit 2 names what it refused; a warning names a retired proposition whose location
will shift. Edit nothing outside the staging directory from here on, and in the staging
directory only these four copies.

`prepare` copies `article.json` too (`docs/OUTLINE.md` of this plugin, "article.json"), as a file
that may not change, when there is one: the one beside the ledger, or, in a run with an outline
(O3, G2), the one in the outline directory. After every `prepare` that succeeds, look whether
`$STAGE/article/article.json` is there, and read it before any manuscript text is written or
changed: its `banned` list names phrasings that are not to appear in the article, each with a
reason. Do not write them. Exit 2 that names `article.json`
means the file is not in its format; say what was printed and stop, the author corrects it.

### W4 — Write the paragraph in the copy

In the staged manuscript file, after the line `prepare` named, add one blank line and the
paragraph: one run of non-blank lines, ending with a line ending. When text follows, the line
after the paragraph has to be blank; add one. Write no other line.

### W5 — Its propositions

Follow steps 1 and 5 to 7 of `/propositions:prop-extract` on the staged manuscript file, over the
lines of the new paragraph. Locations use the staged file's line numbers, which are the numbers
the lines will have after the commit. Then add the lines with the new ids at the end of the staged
ledger:

```bash
cat "$EXTRACT_STAGE/new.ids.jsonl" >> "<staged ledger>"
```

The coverage check runs with `--tex <staged manuscript file> --main <staged main file>`. Any text
it reports uncovered is extracted, or the author accepts leaving it out.

### W6 — Its records

Add one record per new proposition at the end of the staged `discourse.jsonl`, chosen as in
annotate mode (A3): `head` and `relation` inside the new paragraph, `move`, and `opens` or
`discharges` for the commitments W2 agreed. Add the new paragraph to the staged `structure.json`
as annotate mode records a paragraph. Only add to it: `write check` refuses a structure that
loses or changes anything it had.

### W7 — Run the gates on the copies

```bash
"${CLI[@]}" write check --stage "$STAGE"
python3 "$VALIDATOR" --jsonl "<staged ledger>" --meta "$STAGE/ledger/_meta.json" --tex "<staged main file>"
python3 "$VSTRUCT" --jsonl "<staged ledger>" --structure "<staged structure.json>" \
  --discourse "<staged discourse.jsonl>" --partial
"${CLI[@]}" cite-order --jsonl "<staged ledger>" --tex "<staged main file>"
```

All four have to pass: the first three exit 0, and `cite-order` reports no forward citation
that involves a new proposition. A forward citation the draft already had is reported, not fixed
here. When one fails, fix the copies and run all four again. `write check`
prints the lines that hold a placeholder; they are allowed, and the report lists them. A line
`<file>:L<n>: the banned phrasing "…" (<reason>)` is a phrasing of `article.json` in the new
paragraph: reword the paragraph and run the gates again. Do not change `article.json` to make
the check pass; when the author says the phrasing is wanted here, the author changes the list,
and write mode starts again from W3.

Two reports are not about the draft and are not fixed in the copies: an input that changed
after prepare (`article.json`, `_meta.json`, an outline file, or one of its copies), and a
`write.json` that no longer names what prepare copied (`prepare again`). The staging directory
can no longer be used: start again from W3 (O3 or G2 in those modes) in a new one. Never edit
`write.json`, and never edit a staged copy of an input to make a check pass. A launcher
exit of 3 counts as not run, and write mode then stops: nothing is written without the check.

### W8 — Show it and ask once

Show the author:

- the new paragraph as it will stand in the manuscript, with its line numbers;
- the new propositions as a table (location, claim_type, evidence_class, first words);
- the new records (head, relation, move, commitments);
- each example, definition or result of the paragraph whose question nothing before it raises
  (W2), or that there is none, and each sentence written to raise such a question;
- the placeholders and their lines;
- `diff -u` of each of the four files against its copy.

Then ask once (AskUserQuestion): write it, change something, or stop. The answer covers only what
was shown. If anything in the copies changes afterwards, run W7 again and ask again.

### W9 — Write on confirmation

```bash
"${CLI[@]}" write commit --stage "$STAGE"
```

Exit 0 lists the files written and where the originals are kept (`$STAGE/backup/`). Exit 2
writes nothing when the files changed after W3 or the check fails: say why, and start again from
W3 if the author wants to. When the message names files already written, a write failed part
way: report which files were written and where the originals are, and stop. Putting the
originals back is the author's decision; do not do it unasked.

After a commit, the draft has a new end: next mode and write mode start again from it.

### Writing from an outline

When the author asks to write from the outline ("照綱要寫", "write the next paragraph from the
outline"), write mode takes its plan from one paragraph record of an approved outline (the
outline's format: `docs/OUTLINE.md` of this plugin, "Writing text from the outline"). The steps
are W1 to W9, with these differences.

**O1 — Which record.** Establish `OUTDIR`, the directory that holds the outline files, from the
request or by asking once. When `$OUTDIR/article.json` has `destinations`, a part of the article
can be another document (two parts can also name the same one). `outline trace` then checks the
records of the document whose ledger it is given and lists the others as `in the document of the
part <part>`: run it once for the ledger of each document the destinations name, so that a
record written into any of them counts as written. `outline status` takes the directory alone.
Then:

```bash
"${CLI[@]}" outline status "$OUTDIR"
"${CLI[@]}" outline trace "$OUTDIR" --jsonl "$LEDGER/main.jsonl"
```

`outline trace` exits 2 when there is no `outline-trace.jsonl` yet; that means nothing has been
written from the outline. The record to write is the first line of `outline-paragraphs.jsonl`
that does not carry `dropped`, whose section the status shows as `stands as approved`, and that
the trace does not name. Tell the author which record that is, and stop when there is none: a
section that does not stand as approved is approved first, with `/propositions:prop-outline`. Text is
written in the order of the paragraph file; a record further down is written only when the author
asks for it by its id.

**O2 — Instead of W2.** The paragraph says the record's points, in their order, and nothing that
the points do not say. A point with `pending` gets a placeholder `{PENDING: <the pending text>}`
for what it names. A record that carries `carry` is the block its `from` names, copied character
for character, with only the changes its `edits` lists. The rule of W2 on what comes first holds
here too: when a point gives an example, a definition or a result whose question nothing earlier
raises, say so at W8 instead of reordering the record's points, which are the outline's. A citation is the key a point's `basis` or
the manuscript's bibliography gives; any other is a placeholder. When the record is the first of
its section and the section's heading is not in the draft yet, the paragraph comes with the
heading line, written from the section record's `heading`.

The record can plan commitments: `opens` lists the commitments its paragraph opens, each with an
id and a kind, and `discharges` the ids it discharges. The paragraph then does exactly that, and
in W6 its records carry those ids and kinds as written, on the propositions that open or
discharge them. When any record of the outline that is not dropped carries either key and this
one carries neither, its paragraph opens and discharges nothing. When no record carries either,
the commitments are chosen as in W2. `write check` compares the staged records with the plan and
reports each difference (W7): fix the paragraph or its records; a plan that is wrong is changed
with `/propositions:prop-outline` and the section approved again, not here.

**O3 — Instead of the W3 command.** Add the outline, and `--heading` when O2 writes a heading:

```bash
"${CLI[@]}" write prepare --jsonl "$LEDGER/main.jsonl" --tex "$MAIN" \
  --structure "$LEDGER/structure.json" --discourse "$LEDGER/discourse.jsonl" --stage "$STAGE" \
  --outline "$OUTDIR" --outline-paragraph "<record id>" [--heading]
```

Exit 2 names why the record cannot be written from: the outline does not pass `outline check`,
the id names no record or a dropped one, or the section does not stand as approved.

With `destinations` in `$OUTDIR/article.json`, exit 2 can also say that the section goes to a
part and name the `--tex` and `--jsonl` to give: that part is another document. Run `prepare`
again with those two files and with the `structure.json` and `discourse.jsonl` beside that ledger
(ask the author where they are when they are not there; a document with no ledger yet is set up
first, with Operation D of `/propositions:prop-ledger`), and use that document's files in every
later step. Before going on, run the preconditions of W1 (the validator and the structure
validator) on that document's ledger and sidecars: they were run on another document. When it
says that `article.json` names no destination for the part, stop: the author adds one. A run with an outline reads `article.json` from `OUTDIR`, not from the directory of the
ledger.

`prepare` prints a line that begins with `[unread]` for each included file of the record's
section, or of a section above it, that was not read when the outline was derived. Tell the
author at once, before writing: the outline does not say what those files hold, so the section's
plan may leave out what they say. Go on when the author says to, and repeat the lines in W8.

**O4 — Between W7 and W8, the reader.** Write the paragraph record, as one JSON object, to
`$STAGE/outline-record.json`, and the new paragraph, exactly as it stands in the staged
manuscript file, to `$STAGE/paragraph.tex`. Then dispatch the agent `propositions:outline-point-reader`
with a task message that holds those two paths and nothing else. It reports points the paragraph
does not say and results, numbers or citations the points do not state. Show its findings in W8
with the rest; they are a reader's judgment, not a check, and the author decides what to change.
After a change to the copies, run W7 and the reader again.

**O5 — After W9.** `write commit` appends the record to `outline-trace.jsonl` itself; do not
write that file. Run `outline trace` once more and report its count.

When a section record carries `length` or `$OUTDIR/article.json` has `length`, report the
lengths as well:

```bash
"${CLI[@]}" outline length "$OUTDIR" --jsonl "$LEDGER/main.jsonl" --tex "$MAIN"
```

With `destinations`, give `--written` in place of `--jsonl` and `--tex`: each part is counted
from its own document. Report the line of the section just written, the lines of the parts and
the `limit` line, and say which are marked as over. The numbers are an estimate in words and stop
nothing; what to cut is the author's decision.

## Reorganize mode

Reorganize mode rewrites a finished manuscript from its revised outline (`docs/OUTLINE.md` of this
plugin, "Writing text from the outline"): every paragraph of the new text comes from one paragraph
record, sections in the outline's order. It is one write of the whole manuscript behind one
confirmation, through `propositions write prepare --rewrite`. "重組草稿", "照改過的綱要重寫",
"reorganize the draft" mean this mode.

**G1 — The outline first.** The plan is made with `/propositions:prop-outline`, not here: derive the
outline from the manuscript, revise it as the author says, and record the author's approval of the
whole outline. Then establish `OUTDIR` and check:

```bash
"${CLI[@]}" outline status "$OUTDIR"
```

Every section has to stand as approved, and so does the order of sections; otherwise stop and say
that the outline has to be approved as a whole first. The preconditions of W1 hold as well.

**G2 — Prepare.**

```bash
STAGE=$(mktemp -d)/write
"${CLI[@]}" write prepare --jsonl "$LEDGER/main.jsonl" --tex "$MAIN" \
  --structure "$LEDGER/structure.json" --discourse "$LEDGER/discourse.jsonl" --stage "$STAGE" \
  --outline "$OUTDIR" --rewrite
```

It prints the path of `outline-map.jsonl` and of each copy. Edit only the copies from here on.

It prints an `[unread]` line for each included file that was not read when the outline was
derived, for every section; tell the author before rewriting, as in O3. With `destinations` in
`$OUTDIR/article.json`, a rewrite is of one document: give the main file, ledger and sidecars of
that document, and rewrite only the sections that go to it (a section goes to its own `part`,
else to the part of the section it is under, else to `main`). The sections of another document
are rewritten in a run of their own. When the revised outline moves content from one document to
another, rewrite in two runs (issue 133): first the document that receives it, so that its ledger
holds the new propositions, committed; then the document that gives it up, whose retirements name
those propositions in the other ledger (G4). Tell the author the order before the first run. `prepare` also refuses when any
section that is not dropped goes to a part for which `article.json` names no destination, even a
section of another document: stop and tell the author which part needs one.

**G3 — Rewrite the copies.** Follow the outline: its sections in order, each with its heading
line, and in each section its paragraph records in order. A record that carries `carry` is the
block its `from` names, copied character for character with only the changes its `edits` lists. Any
other record says its points, in order: where a sentence of the passages its `from` names still
says a point, keep that sentence as it is written, so that its proposition is found again in G4.
A point with `pending` gets `{PENDING: <the pending text>}`; results, numbers and citations follow
the rules of O2, and so does what comes first (an example, a definition or a result whose question
nothing earlier raises is told to the author in G8). Keep what is not a paragraph as it was: the preamble, `\begin{document}`, the
title, the bibliography, `\end{document}`. Change an included file only when the outline moves
text into or out of it.

**G4 — Bring the ledger up, in the copies.** Run the revision mode of `/propositions:prop-extract` (R1
to R6 there, and R8 for the new propositions) on the staged ledger and the staged main file, with these choices:

- In its retire step, the replacements of a proposition that is not found again are the new
  propositions of the paragraph whose record names, in `from`, the passage the proposition stood
  in. A proposition in a passage no record names is retired with no replacement: its text was
  dropped. Say which propositions are retired and with what.
- Run its commands on the staged paths (`--jsonl <staged ledger> --tex <staged main file>`), never
  on the ledger.
- When the passage moved to another document (the second of the two runs), its replacements are
  the propositions that the first run wrote in that document's ledger: write each one
  `<ledger>#<id>`, the path relative to the directory of the original ledger (not of the staged
  copy), and give `revise retire`, `revise redirect` and `revise check` `--ledger-dir "<directory
  of the original ledger>"`, in this run and in every later rewrite of this document. A citation
  is not carried into the other ledger: `redirect` drops it and says so. The propositions of a
  moved paragraph are those of the other ledger from the `first_prop` the first run traced for
  it, in reading order, up to the next traced paragraph.
- When `revise check` reports an item of another ledger that is retired (the receiving document
  retired it later), no command can change that retirement and the rewrite refuses to: stop and
  tell the author that the retirement in the original ledger has to be edited by hand, outside
  a rewrite, before this document can be rewritten.

**G5 — Rebuild the sidecars, in the copies.** The paragraphs changed, so `discourse.jsonl` and
`structure.json` are annotated again for the new text, as annotate mode does (A2 to A4), in the
staged copies.

**G6 — The map.** Write `$STAGE/outline-map.jsonl`: one line `{"outline": <record id>,
"first_prop": <id>}` per paragraph record that is not dropped, in the order of the paragraph file,
naming the proposition that starts the paragraph written from it. With `destinations`, list only
the records whose sections go to the document being rewritten.

**G7 — The gates, on the copies.**

```bash
"${CLI[@]}" write check --stage "$STAGE"
python3 "$VALIDATOR" --jsonl "<staged ledger>" --meta "$STAGE/ledger/_meta.json" --tex "<staged main file>"
python3 "$VSTRUCT" --jsonl "<staged ledger>" --structure "<staged structure.json>" --discourse "<staged discourse.jsonl>"
"${CLI[@]}" revise check --jsonl "<staged ledger>" --ledger-dir "<directory of the original ledger>"
"${CLI[@]}" cite-order --jsonl "<staged ledger>" --tex "<staged main file>"
```

Run the structure validator with `--partial` only when the manuscript was unfinished before the
rewrite. All five have to pass (`cite-order` as in W7). When one fails, fix the copies and run them
all again. On a rewrite `write check` also reports a banned phrasing of `article.json` anywhere in
the staged manuscript, a paragraph that does not open and discharge what its record plans (when
the outline plans commitments), and a file the staged manuscript includes that `prepare` did not
copy: a rewrite cannot add a file to the input tree.

**G8 — The readers, then show it and ask once.** For each paragraph written from a record (not a
record that carries `carry`), dispatch `propositions:outline-point-reader` as in O4, the record and
that paragraph in two files of the staging directory; dispatch them together. Then show the author:

- `diff -u` of every file that changed against its copy (the main file, any included file, the
  ledger, the two sidecars);
- how many propositions were found again, retired (and with which replacements), and added;
- the placeholders and their lines;
- each example, definition or result whose question nothing before it raises (G3), or that there
  is none;
- the readers' findings, record by record.

Ask once (AskUserQuestion): write it, change something, or stop. A change to the copies runs G7
and the readers again, then asks again.

**G9 — Write on confirmation.**

```bash
"${CLI[@]}" write commit --stage "$STAGE"
```

It writes the files that changed and writes `outline-trace.jsonl` anew from the map. With
`destinations`, the records of the other documents are kept as they were, before the records of
the map, which then carry their `part`: those kept records are not stale. The originals
are in `$STAGE/backup/`, and `backup/restore.jsonl` says where each came from (the old trace
included). When a write fails part way, report what was written and that list, and stop: putting
the originals back is the author's decision. Then run `outline trace` and report its count, and
the lengths as in O5 when the outline or `article.json` has a `length`.

When the author changes the `banned` list of `article.json` after text was written, a document
is compared with `"${CLI[@]}" phrasing --tex "$MAIN" --article <the article file>`: it reads the
input tree of that main file and no other, so with `destinations` run it once for each main
file they name, and say which document could not be compared. Exit 1 lists each occurrence
with its line. Report them; rewording them is a revision the author
asks for.

## Explain mode

### E1 — Preconditions: sidecars for this text

```bash
[ -f "$LEDGER/structure.json" ] && [ -f "$LEDGER/discourse.jsonl" ] || echo "no sidecars in the ledger directory"
```

If either file is missing, say that the sidecars are missing and offer annotate mode. Write
nothing and stop here. Otherwise fingerprint every file this mode must leave alone:

```bash
BEFORE=$(shasum -a 256 "$MAIN" "$LEDGER/main.jsonl" "$LEDGER/structure.json" "$LEDGER/discourse.jsonl")
```

### E2 — Find the paragraph or section

Take the paragraph id or section id if the user gave one; a heading gives a section id through
`sections` in `structure.json`. If the user quotes a sentence, look for a short phrase of it
without markup:

```bash
python3 "$EXPLAIN" --jsonl "$LEDGER/main.jsonl" --all --format json | python3 -c '
import json, sys
for par in json.load(sys.stdin)["paragraphs"]:
    if any(sys.argv[1] in p.get("text", "") for p in par["propositions"]):
        print(par["id"], par["section"], par["section_heading"])
' "$PHRASE"
```

If this finds nothing, or several paragraphs and the request does not say which, ask once.

### E3 — Run the tool and show its output

```bash
python3 "$EXPLAIN" --jsonl "$LEDGER/main.jsonl" --paragraph "$ID"   # or --section "$ID", or --all
```

Show the output as it is. Each line gives the position, what the sentence does, and what it
hangs on with the relation in plain words and by name. Indentation is depth in the paragraph's
tree. `段根` marks the paragraph's root, `未標` a sentence with no `move`, and `另：` an `also`
entry. Exit 2 prints why: an unknown id, version 1.0 sidecars, sidecars that fail S1, S2, S3 or
S5, or PyYAML missing. Report the message and do not repair anything here; annotate mode
converts or fixes the sidecars.

For one sentence ("這句跟哪些句子有關", "what does this sentence connect to"), also run:

```bash
python3 "$LINKS" sentence --jsonl "$LEDGER/main.jsonl" --at "$POSITION"
```

It lists every link of that sentence beyond its paragraph too: its head and the sentences that
hang on it, the sentences before and after it, `also` entries, citations both ways, and the
commitments it keeps or opened. Each line says the kind, the other sentence, the relation and
whether the other end is in the same paragraph, the same section or another section. To see
how often a move is followed by another across the reference manuscripts, and which moves have
never been seen after it, use `python3 "$LINKS" catalog --from <move> --kind next --unseen`;
say that these are observed counts from two manuscripts, not rules.

### E4 — Say it in plain language

Below the output, say:

1. **What the paragraph does**, from its `type` and the moves of its sentences.
2. **Which sentence the others hang on**: the root, the sentences that hang directly on it, and
   any longer line under them, by position.

For a section, do this for each paragraph and add how the paragraphs hang on each other. Say only
what the output and the sentences support. If the sentences show `未標` or the paragraph has no
type, say that those labels are missing and that what you say about the paragraph is your own
reading of the sentences, and offer annotate mode. Explain mode describes the paragraph; it does
not judge it.

### E5 — Leave every file untouched

```bash
AFTER=$(shasum -a 256 "$MAIN" "$LEDGER/main.jsonl" "$LEDGER/structure.json" "$LEDGER/discourse.jsonl")
[ "$BEFORE" = "$AFTER" ] || echo "a file changed in explain mode — stop and report"
```

Explain mode writes nothing: not the manuscript, not the ledger, not the sidecars.

## Report

- **Annotate**: validator results (propositions ledger and structure), the A5 summary, the
  close calls, where the sidecars were written (or that the user declined and where the
  staged files are), and the `main.jsonl` fingerprint check.
- **Next**: the state (section, role, open commitments), the move hint or why it was skipped,
  the candidates, and the fingerprint check.
- **Write**: what the paragraph does (from an outline: the record's id, and the reader's findings
  with what the author decided), the gates (W7), what was written and where the originals
  are, or that the author stopped and where the copies are. List every placeholder with its
  line: the paragraph is not finished while one remains. Say that the paragraph was checked
  mechanically and not proofread; `/propositions:prop-proofread` and `/propositions:prop-clarity-audit`
  run when the author asks.
- **Reorganize**: the outline's status, the counts of G8, the gates (G7), the readers' findings and
  what the author decided, what was written and where the originals are (`backup/restore.jsonl`),
  or that the author stopped and where the copies are; every placeholder with its line.
- **Explain**: the tool's output, the plain-language reading, and the fingerprint check.
